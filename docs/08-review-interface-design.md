# Review Interface — Design

Status: implemented (`src/cbdb_agent/review.py`, `tools/review/index.html`, CLI
`apply-review`). Written 2026-08-18, while preparing a 78-proposal / 41-conflict
batch of 元代 person records — the first batch big enough that reading `preview.md`
top to bottom stopped being a usable review.

## 1. Problem

`docs/06-staging-preview-design.md` gave us `preview.md`: a generated, read-only
Markdown summary with a live old-vs-new diff. That was the right answer for a
1–2 proposal batch. At 78 proposals it isn't:

- **It's a 67 KB linear document.** The user's stated requirement is
  「希望能縱覽式的看大量數據，而不是一條一條看」 — see a lot of data at once, not one
  record at a time. A long scroll is exactly one-record-at-a-time.
- **Repeated questions get answered repeatedly.** That batch has 5 separate
  `c_index_year` conflicts asking the *same* question (what is this project's
  index-year convention?) and 3 separate reign-year arithmetic checks. In Markdown
  they are 8 unrelated-looking paragraphs 40 KB apart.
- **There's nowhere to answer.** `preview.md` is read-only by design, so every
  decision has to be relayed through chat or hand-edited into nested YAML. The user
  asked for the opposite: 「遇到問題我希望在界面裡面進行互動或者修改」.
- **No cross-cutting view.** "Show me every `low`-confidence row", "every row that
  touches an office code", "everything still unresolved" — all unanswerable without
  reading the whole file.

## 2. What was decided, and what was rejected

### A reusable page that *loads* JSON, not a page generated per batch

`docs/06` Tier 3 suggested rendering `preview.md` as a session Artifact. That is a
nicer *read*, not a review tool, and it has to be regenerated (and re-trusted) every
batch. Instead: **one HTML file committed to the repo** at `tools/review/index.html`,
which loads a batch's `review.json` at runtime.

Why this way round:
- **The page accumulates.** Filters, bulk resolution, keyboard flow — all improve
  once and apply to every future batch. A per-batch generated page throws that away
  each time, and each regeneration is a fresh chance to render something wrong.
- **Future tasks are not just creates.** The user has flagged that modification
  tasks are coming. A generic page keyed off the staging schema handles
  `update`/`delete` and the current-vs-proposed diff with no new work; a
  create-shaped generated page wouldn't.
- **The page holds no data.** It is reviewable as code, once. The unpublished
  historical data stays in gitignored `data/staging/` and is only ever read from a
  local file the reviewer picks.
- **No server, no build, no network.** Single file, no dependencies, opens from
  `file://`. This gets used on a laptop, offline, on data that must not be uploaded
  anywhere — every one of those constraints rules out a dev server or a CDN.

### The YAML stays the only source of truth, and the only write path

This is the constraint `docs/06` §4 set ("editing via the preview" out of scope), and
it still holds — but it is now satisfied by a *round trip* rather than by making the
review surface read-only:

```
proposal.yaml  ──validate --staging──▶  review.json  (generated, disposable)
                                             │
                                    tools/review/index.html
                                    (human reviews, decides, edits)
                                             │
                                       decisions.json  (the human's output)
                                             │
proposal.yaml  ◀──apply-review───────────────┘
                    (prints every change it made)
```

- `review.json` is generated by the same `validate --staging` run that refreshes
  `preview.md`, for the same reason: **a review surface that can go stale relative to
  the file it describes is worse than none.** No separate `export` command to forget.
- The page cannot write the YAML — it's a `file://` document with no filesystem
  access. That is a feature, not a limitation worked around.
- `apply-review` is the only reader of `decisions.json`, and it prints one line per
  change. So the diff a reviewer's clicking produced is visible *before* they
  re-validate, and `git`-invisible data still gets a human-readable changelog.
- **`submit` still reads only the YAML.** Nothing in the review path can produce a
  submittable batch that didn't go through `validate`.

### Validation semantics stay in Python, exactly once

`review.json` ships pre-computed `resolved` flags, `needs_approval`, person grouping
and the current/proposed pairing. The page never re-derives them. Two
implementations of "is this conflict resolved" would drift, and the Python one is the
one that actually gates submission.

The page does carry a `schema_version` check and refuses a payload it doesn't
understand, rather than mis-rendering a newer shape.

## 3. What the page does that the Markdown could not

- **Dense table, grouped by person**, collapsible, sticky headers. A person and
  everything proposed about them is one block.
- **Bulk resolution of repeated questions.** Conflicts are fingerprinted by
  `field` + option set; any fingerprint appearing more than once surfaces at the top
  as one row with the option buttons and a count. The 5 index-year conflicts become
  one click. This is the single highest-value feature for a batch this size.
- **Filters and search**: resource, operation, confidence, "only unresolved", "only
  edited by me", plus free text across ids, names, field values and source quotes.
- **Inline decisions**: option chips (the agent's suggestion visually distinct), a
  free-text override, `defer`, and undo. Each option's rationale is shown, not
  hidden in a tooltip only.
- **Inline field editing**, with the original value struck through when the row is an
  update and a live value was fetched.
- **The approval gate is visible.** An approval-gated proposal (`AGENTS.md` rule 12)
  renders a locked panel that says what the risk is and takes the reviewer's name.
  The agent is not permitted to fill this in, and the page is where the human does.
- **Typed values survive.** `18` stays an int, `[18354]` stays a list, `null` and
  `""` are rendered *differently* — they mean different things to this API
  (`API.md` §1.4), and a reviewer must be able to tell them apart.
- **Decisions persist in `localStorage`** per batch, so a stray reload doesn't lose
  an hour of review.

## 4. Deliberately out of scope

- **Submitting from the page.** It cannot reach the network, and it must not: the
  dry-run and `CBDB_CONFIRM_PROD` gates live in the CLI (`AGENTS.md` rule 4), and a
  second submission path would be a second place for them to be missing.
- **Editing `target_pk`, `resource`, or `operation`.** Those are structural. Changing
  them is a different edit from resolving a question about a value, and the honest
  way to do it is in the YAML, where it will be re-validated from scratch.
- **Adding or deleting whole proposals.** Same reasoning. `defer` covers "don't
  submit this row".
- **Replacing `preview.md`.** It still stands alone with no browser, and is what a
  terminal-only or CI context reads. Tier 1 must keep working (`docs/06` §2).

## 4a. One coupling to keep in mind

`review.REVIEW_JSON_SCHEMA_VERSION` and the page's `const SCHEMA` must match. The page
refuses to load an export whose version it doesn't recognise, which is the right
behaviour — better a clear refusal than a silent mis-render — but it also means
bumping one and forgetting the other turns the page into a blank screen that passes
every syntax check. `tests/test_review_page.py::test_page_declares_the_same_schema_version_as_the_exporter`
exists precisely because that happened.

Bump both together, and add a line to the `//` history next to the constant saying
what changed, so a future reader can tell whether an old `review.json` lying around is
merely stale or actually incompatible.

## 5. Files

```
src/cbdb_agent/review.py         export_review_json() / apply_decisions()
tools/review/index.html          the page (no data, no dependencies, no network)
src/cbdb_agent/cli.py            validate --staging also writes review.json;
                                 new `apply-review --staging <yaml> --decisions <json>`
tests/test_review.py             export shape, apply strictness, round trip
tests/test_review_page.py        the page itself, driven in headless Chromium
```

`apply_decisions()` is **strict**: an unknown proposal or conflict id, a foreign
`batch_id`, or a mismatched `schema_version` is a hard refusal, not a partial apply.
A decisions file that no longer matches its batch means one of the two has moved on,
and applying only the half that still matches is how a reviewer ends up believing
they settled something they didn't.
