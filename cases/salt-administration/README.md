# Ming/Qing salt administration

Enter the six Ming and Qing 都轉運鹽使司 and their 分司 into CBDB as **place names**,
with each unit's coordinate copied from its 治所 and its parent recorded as a
hierarchy edge.

**Source of the request:** Ning Hao's compilation,
`明清六個鹽運使司情況（完整版）.xlsx`. The spreadsheet is not in this repo — it is
unpublished source material, and `case.py` names the sheets it reads rather than
carrying the data.

**Design:** `docs/11-salt-administration-design.md`.

### Why the first batch was dropped

Track A entered each unit as an `OFFICE_CODES` row. On 2026-09-11 that was abandoned:
a separate import had already covered the salt-administration **post titles**, and
Ning Hao's list names the **institutions**, which belong in the place-name tables —
which was his proposal to begin with. `emit_offices.py` still exists and its `main()`
refuses to run, so the reasoning is readable and the batch is not re-creatable by
accident.

### Where the second batch stands

2 `ADMIN_CAT_CODES` + 57 `ADDR_CODES` + 59 `ADDR_BELONGS_DATA`, submitted to
production on 2026-09-18. It stopped at proposal 12 on
`SSLError(SSLEOFError(8, '[SSL: UNEXPECTED_EOF_WHILE_READING]'))` — an **indeterminate
write**, which per AGENTS.md rule 11 is not retried and stops the whole batch.

Reconciled two ways afterwards (`GET /api/v2/operations`, and
`GET /api/select/search/addr` for the one uncertain row). What landed:

- `ADMIN_CAT_CODES` **226** 都轉運鹽使司 and **227** 分司
- `ADDR_CODES` **702716–702724** — nine 明代 兩淮/兩浙 rows
- no `ADDR_BELONGS_DATA` edges at all
- the 12th proposal (`長蘆都轉運鹽使司`) did **not** land: no `operations` row, and an
  exact-name search returns zero

So **11 of 118 rows are in production** and 107 are not. The production write gate is
re-locked (`CBDB_DRY_RUN=true`, `CBDB_CONFIRM_PROD` empty).

### Complete — all 118 rows are in production

2 `ADMIN_CAT_CODES` (226 都轉運鹽使司, 227 分司), **57 `ADDR_CODES`** and
**59 `ADDR_BELONGS_DATA`** edges, over five runs. Verified independently
afterwards: all 57 places are live under their own name *and period*
(`GET /api/select/search/addr`, 57/57), and `GET /api/v2/operations` shows exactly
59 `ADDR_BELONGS_DATA` and 2 `ADMIN_CAT_CODES` entries.

It took five runs because four were cut short mid-flight by a dropped connection
— see "The network, and what it cost" below. Every interruption left one
indeterminate row, each reconciled against `operations` with a control before the
next run, and no row was created twice.

**Still owed:** `php artisan cbdb:regenerate-addresses-table` on the server.
`ADDRESSES` is a derived cache, so until it is rebuilt these 57 places stay
invisible to posting autofill and dynasty homonym disambiguation.

### The network, and what it cost

Runs stopped at proposals 12, 69, 16 and 4, each with a dropped TCP connection and
no HTTP status. A controlled comparison — 120 identical requests at 1/s, back to
back — showed the local proxy failing at request 38 while direct ran 120/120, so
`http_client` now connects directly and ignores every ambient proxy setting
(AGENTS.md rule 2). That is a real improvement and not the whole answer: the
fourth run was verifiably direct and still failed after four writes. Reads are
reliable on the direct path, sustained writes are not, and it is not
application-level throttling — that answers `429`, which no run ever saw.
Unresolved.

### The resume batches

`2026-09-19-salt-addresses-resume` holds the 107 rows the first run did not send,
generated by `python -m cbdb_agent resume` from the submitted `proposal.yaml` and
its `results.json`. The 11 that landed are not repeated, and every reference to one
of them is now the id the server assigned: the 48 address creates carry
`c_admin_cat_code` 226/227 directly, and 7 of the 59 edges had their parent
rewritten to a real id (702716, 702720). The other edges point either at a row
still in this batch or at a dynasty root, which was always a literal. It validates
clean. **Nothing has been submitted.**

`data/processed/2026-09-18-salt-addresses/reconciliation.json` records the one
indeterminate row — `addr-ming-長蘆-長蘆都轉運鹽使司-1373` — as never written, with
the two checks that establish it. `resume` refuses to run without that file.

### A defect the SSL error was hiding

The batch could not have completed even without the network failure.
`preflight.assert_addr_create_is_not_a_duplicate` refused any live `ADDR_CODES` row
with a matching `c_name_chn`, but this table holds **one row per place per period**
(design §5.1): 19 of the 32 names here are two or three rows with disjoint years.
So the moment a unit's first seat period landed, its second was refused as a
duplicate of it — **25 of the 57 address rows were unreachable**. The run stopped at
proposal 12; the first collision would have been proposal 14.

Fixed on both sides: a duplicate is now the same name over an *overlapping* period,
in the submit-time guard and in the generator's check alike.

### What is still owed

`php artisan cbdb:regenerate-addresses-table` on the server — see above.

## Code

`case.py` — this job's content: the source note and id, the two dynasty windows, the
seat name variants and disambiguation boxes, the settled seat decisions, the blocked
units, the successions, the naming/translation/romanization conventions, and the
reader for this particular spreadsheet.

The method it plugs into is `src/cbdb_agent/places_and_offices/`, which knows nothing
about salt. Run it from the repo root:

```
python -m cbdb_agent.places_and_offices.build_dataset \
    --case salt-administration --xlsx <path to the xlsx>
python -m cbdb_agent.places_and_offices.emit_addresses \
    --case salt-administration --batch-id <batch id>
```

The first writes `data/build/salt-administration/` (gitignored); review it at
`review/dataset.html?case=salt-administration`. The second writes
`data/staging/<batch-id>/proposal.yaml`.
